## Fix And Boundaries

- A completed ANSWER_FROM_CONTEXT plan with explicit no-retrieval can remain
  history-only when owned history exists and there are no current inputs/targets
  or executed/rejected/deduplicated/unfinished READs requiring normal recovery.
- History is not promoted to current grounding evidence or write authority.
  Actual searches retain existing source, scope, fan-out and authorization checks.
- Parallel READ planning now receives the server-owned
  ragRequiredWithReadActions catalogue field and instructions to select exact
  authorized indexed namespaces on that existing path. Action/source identifiers
  are not inferred to be namespaces. No automatic search-all is added.
- Extraction guidance distinguishes transforming supplied earlier content from
  obtaining fresh facts. No phrase matching or forced intent replacement is used.
- Routing failures retain planner diagnostics, actual READ receipts and original
  failure status. Invocation-parameter fields are omitted on this newly exposed
  diagnostic path; public JSON still excludes internal pinned-target fields.

No UI redesign, knowledge rewrite, database migration, reindex or new business
permission is part of this fix. The original reported request and conversation
remain read-only. Support's ten saved configuration sections are snapshotted and
must be unchanged at publication. Existing app, customer and target identities
must be retained.

## Open Source-Catalogue Finding

The new routing diagnostics distinguish this first-question failure from the
history-only follow-up defect:

1. Extraction first selected plugin/source ID `approved-support-documents` as a
   namespace. Validation correctly rejected that unregistered name.
2. Bounded model repair retained requiresRetrieval=true but supplied no namespace.
3. The READ planner saw an empty source catalogue and reported no authorized
   indexed sources. It selected ANSWER_FROM_CONTEXT, with no history/evidence.
4. Normal retrieval still required a source and returned domain clarification.
   The 0.8.54 history-only exception correctly did not bypass fresh-evidence
   requirements for this empty-history request.

Code trace: OrchestrationPolicyResolutionStep calls resolveLegacy on the default
capability resolver. That legacy profile derives effectiveVectorSpaces only from
the optional retrieval allowlist. An absent optional allowlist therefore produces
an empty set. ReadActionResolutionService starts with registered namespaces but
intersects them with that empty effective set, hiding `document` from the planner.
The successful first sample's normal routing independently recognized exactly
one namespace, `document`, and used it. Thus the catalogue's empty list is not
proof that the index or customer permission is missing.

Recommended separate bounded correction: make the ordinary-chat legacy profile
use the same server-authoritative registered/authorized source catalogue as
routing when its optional allowlist is absent. Preserve configured allowlists,
required-allowlist rules, explicit task-profile empty-set denials and actual
search authorization. Do not hardcode `document`, map arbitrary plugin IDs to
namespaces, weaken the empty-history guard or replace the clarification with an
ungrounded canned answer. Add regressions for both legacy discovery and explicit
denials, real-provider checks, then fresh staging/production qualification.

This additional framework change was proposed for owner approval; it is NOT
implemented or released in 0.8.54. The known source-selection miss predates this
release; 0.8.54 adds evidence explaining the mismatch. Production remains on the
healthy bounded follow-up improvement, not an asserted fully qualified journey.

The existing COLD_REPLACE lifecycle may restart Support; do not describe the
