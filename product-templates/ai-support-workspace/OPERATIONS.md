# AI Support Workspace Operations

This is an operator runbook, not an indexed support document or a promise that
every deployment has been launched. Exact live identities, releases, results and
remaining gates belong in the 010.54 execution record. Credentials stay private.

## Internal LoomAI Launch Policy

The owner approved the following initial posture through Required for production
on 2026-10-31:

- Mahmoud owns the receiving human-support queue. Support is owner-operated and
  best effort, with no promised response time or always-available staffing.
- Explain that submitting the form starts AI-assisted support. Human support can
  be requested. Do not ask customers to submit passwords, tokens, raw environment
  files or private customer records.
- The retention policy target is **360 days after case closure**. This is not
  evidence of automatic deletion across Platform, runtime, Desk, backups or model
  providers. Removal requests require human review and a separately verified
  cross-store operation; do not describe Cancel or Resolve as erasure.

This policy is for LoomAI's own instance only. A customer using the reusable
template supplies its own support staffing, disclosure and retention policy.

## Enable And Verify

1. Publish the reviewed DATA dependency and template. Keep internal diagnostic
   tools separate from the customer-reusable starter and bind no internal secret
   to another customer's installation.
2. Bind that deployment target's approved read-only source prefix and a durable
   vector provider. For shared infrastructure, use the provider's supported
   tenant/namespace format and normal customer/target isolation. Do not reuse an
   unavailable historical verification endpoint.
3. Discover, approve/register, preview, index and reconcile the intended documents.
   Check ACTIVE versions and actual retrieval evidence. Accepted work is not a
   successful index. Retain failed work and explicitly qualify a correction
   before retrying it.
4. Pass the exact applied release's normal verification. Enable Desk through the
   existing deployment integration; a customer OWNER must separately assign a
   registered agent the SUPPORT role. Ownership alone is not permission to reply.
5. Connect an ordinary generic Engage installation to the verified target/release.
   The Console case-host path is backend-mediated and keeps runtime credentials
   and assertions server-side. No special support widget or second transcript
   database is required.
6. Configure the exact internal owner/tenant/deployment/target, installation and
   assertion policy. Diagnostics and optional Desk context use distinct owned
   credentials. Register only the approved callback origin and binding.
7. Verify actual intake, cited help, consent-bound checks, human handover, a Desk
   reply arriving without reload, explicit AI return, resolve/reopen and requester
   isolation. Verify reload does not resend the form or replay an action.

## Queue And Case Handling

An agent claims a waiting conversation through Desk. If nobody is available,
report the queue state honestly; a timeout is not resolution. AI must not answer
while the human owns the conversation. Returning to AI requires an explicit
authorized transition.

Desk Close ends the runtime conversation, not the business support case. Resolve
or Cancel changes the case lifecycle and revokes diagnostic consent. Reopening
does not restore consent. A terminal episode requires an explicit new conversation
episode; never reset the old transcript or replay its intake to simulate reopening.

Use only the selected, currently owned resources for diagnostics. Revocation
blocks future checks but cannot erase an observation already shown in the chat.
Unavailable source storage, incomplete checks and uncertain outcomes must remain
visible rather than becoming a guessed healthy state or an automatic repair.

## Corrections And Removal Requests

For a document correction, upload approved replacement bytes in the owned source
storage, refresh the registered revision, preview, index and reconcile. Verify the
new evidence before retiring the previous derived version. Index removal never
deletes the customer's original object.

For a personal-data removal request, first verify the requester and identify the
case, all linked conversation episodes and its Desk binding. Record the request
and human decision without copying the transcript into a second tracker. Check
each store's actual supported removal process and backup/provider limitations.
An unavailable removal operation is a named follow-up, not permission to delete
one registry row and claim complete erasure. There is no automatic cross-store
retention/erasure guarantee in the initial launch contract.

Runtime canonical history remains the transcript authority; Platform stores
minimal intake/lifecycle/consent and episode references; shared Desk stores its
human-channel projections; Supabase supplies identities and sessions. No database
is created for each case or requesting customer.
