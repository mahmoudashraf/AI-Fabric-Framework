# Deployment-Scoped Provider Secret Overrides Plan

Status: reviewed, design-locked planning document (2026-04-05)

This document is the concrete planning baseline for **Wave 4 Track D**:

- deployment-scoped provider secret overrides

Current sequencing intent:

- Track B remains the active delivery track until verification closure is stable
- **Track C is intentionally skipped for the next review/execution pass**
- Track D is the next design-locked execution target after Track B closure

This plan is intentionally detailed enough to review before implementation starts.

---

## 1) Problem Statement

Today the platform mostly resolves provider credentials from global platform secrets.

That model is acceptable for:

- internal demos
- platform-owned verification fleets
- shared operator-controlled vendor accounts

It is not good enough for:

- customer-owned provider credentials
- environment-specific vendor billing ownership
- reduced blast radius during rotation
- deployments that must not share one vendor key with unrelated deployments

The platform already has one partial version of this pattern:

- deployment-scoped managed secrets generated by the platform for managed vector resources

Track D generalizes that model into an operator-visible, governed capability for selected provider credentials.

---

## 2) Product Goal

Allow a deployment to override selected provider secrets while keeping global platform secrets as the default model.

Desired operator behavior:

- global platform secrets remain the default fallback
- selected deployments may point to deployment-owned secret references
- raw provider credentials never appear in deployment draft JSON or published artifacts
- effective credential source is visible in diagnostics, verification, and readiness
- hard delete can clean deployment-owned overrides without touching unrelated global secrets

---

## 3) Scope

### 3.1 In scope for Track D

- deployment-scoped override references for selected provider secrets
- one secret store model with explicit scope metadata
- effective resolution precedence and diagnostics
- deployment-aware secret usage visibility
- deployment-aware validation and release verification
- provider and secrets UI for override management
- hard-delete cleanup for deployment-owned overrides
- regression and live verification for override behavior

### 3.2 Out of scope for Track D phase 1

- arbitrary secret templating inside drafts
- free-form secret references for any env var
- customer self-service secret portals
- assistant-driven secret mutation flows
- secret-sharing graphs across multiple deployments
- full management-plane credential overrides for all cloud vendors

### 3.3 Keep explicitly out of Track D phase 1

- raw secret values in deployment config
- draft JSON carrying secret material
- hidden fallback behavior with no diagnostics
- auto-migrating all deployments to overrides

## 4) Explicit Decisions

These decisions should be treated as locked unless review finds a concrete reason to change them.

### 4.1 One secret store model

Use a single platform secret model with explicit scope and ownership metadata.

Do not create a second independent deployment-secret subsystem unless implementation forces it.

### 4.2 Dedicated binding table

Deployment override references must persist in a dedicated binding table.

Do not persist override references in:

- `providerConfigJson`
- versioned deployment config metadata
- ad hoc provider-specific secret-name fields

This is a locked design decision, not an implementation preference.

### 4.3 Reference-only deployment config

Deployment config must store only secret references or secret-purpose bindings.

It must never store:

- secret values
- masked secret placeholders pretending to be values
- provider credentials in providerConfig JSON

### 4.4 Explicit secret purpose catalog

Overrides should be allowed only for an explicit supported-purpose list.

Do not allow arbitrary secret-name injection in phase 1.

### 4.5 Paired credentials must resolve atomically

Some credentials are operationally one contract even if stored as multiple secret rows.

For phase 1, Milvus or Zilliz runtime credentials must be modeled as one paired override purpose and must not be independently bound or resolved.

### 4.6 Deterministic precedence with explicit binding mode

Resolution precedence must be explicit:

1. deployment override
2. deployment-managed secret generated by the platform
3. global platform secret
4. environment fallback only where the platform already allows it

Each deployment binding must also declare whether fallback is allowed:

- `REQUIRE_OVERRIDE`
- `ALLOW_STANDARD_PRECEDENCE`

### 4.7 Runtime/provider focus first

Phase 1 should focus on provider/runtime/data-plane credentials.

Keep management-plane secrets global longer unless there is a clear customer-isolation reason to override them.

### 4.8 Deployment-admin write boundary

Phase 1 must keep raw override value mutation platform-admin only.

Deployment admins may:

- bind an allowed override to their assigned deployment
- unbind an allowed override from their assigned deployment
- inspect effective source and missing-binding diagnostics

Deployment admins may not:

- create raw secret values
- rotate raw secret values
- delete secret rows that may be reused elsewhere

### 4.9 Cleanup must be first-class

Hard delete must understand deployment-owned override secrets from day 1.

This cannot be bolted on later.

## 5) Current State Summary

Today the platform already distinguishes between:

- global platform secrets such as:
  - `OPENAI_API_KEY`
  - `PINECONE_API_KEY`
  - `QDRANT_CLOUD_MANAGEMENT_API_KEY`
  - `WEAVIATE_API_KEY`
  - `ZILLIZ_CLOUD_API_KEY`
- deployment-managed secrets such as:
  - deployment-scoped Pinecone runtime secrets
  - deployment-scoped Qdrant database API keys
  - deployment-scoped Milvus credentials

What is missing today:

- deployment-owned operator-provided overrides
- explicit effective-secret precedence
- UI visibility of effective credential source
- deployment-aware secret cleanup for non-managed override secrets

## 6) Target Capability Model

The platform should support three practical secret scopes:

- `GLOBAL_PLATFORM`
- `DEPLOYMENT_OVERRIDE`
- `DEPLOYMENT_MANAGED`

Optional environment fallback remains an implementation detail, not an operator-facing primary scope.

### 6.1 Secret resolution examples

Example A:

- deployment `dep-a` uses global `OPENAI_API_KEY`
- effective source: `GLOBAL_PLATFORM`

Example B:

- deployment `dep-b` uses `DEPLOYMENT_OVERRIDE` for OpenAI
- effective source: `DEPLOYMENT_OVERRIDE`

Example C:

- deployment `dep-c` uses platform-managed Qdrant
- runtime data-plane key comes from a platform-generated deployment-managed secret
- effective source: `DEPLOYMENT_MANAGED`

---

## 7) Supported Override Purposes For Phase 1

Phase 1 should support overrides only for credentials that make operational and enterprise sense.

Recommended supported purposes:

- `OPENAI_API_KEY`
- `AZURE_OPENAI_API_KEY`
- `ANTHROPIC_API_KEY`
- `COHERE_API_KEY`
- `GEMINI_API_KEY`
- `PINECONE_API_KEY`
- `WEAVIATE_API_KEY`
- `QDRANT_API_KEY`
- `MILVUS_RUNTIME_CREDENTIALS`

`MILVUS_RUNTIME_CREDENTIALS` is a paired override contract.

It may still materialize as two stored secret rows internally, but bind or resolve as one deployment override purpose.

### 7.1 Paired credential rules

For paired purposes:

- both underlying secrets must be present together
- the binding resolves atomically
- fallback applies to the credential pair, not one field at a time

### 7.2 Keep global only in phase 1

These should stay global in phase 1 unless a reviewed exception is added:

- `QDRANT_CLOUD_MANAGEMENT_API_KEY`
- `ZILLIZ_CLOUD_API_KEY`
- `PLATFORM_ARTIFACT_SIGNING_KEY`
- deployment-ingress auth keys like `CONNECTOR_API_KEY`

Reason:

- these are management-plane or platform-wide operational keys
- expanding override scope to them too early creates more governance risk than value

## 8) Recommended Data Model

### 8.1 Secret entity extension

Extend the platform secret model with explicit ownership metadata.

Recommended fields:

- `scopeType`
  - `GLOBAL_PLATFORM`
  - `DEPLOYMENT_OVERRIDE`
  - `DEPLOYMENT_MANAGED`
- `deploymentId` nullable
- `secretPurpose`
  - example: `OPENAI_API_KEY`, `PINECONE_API_KEY`
- `ownerType`
  - `PLATFORM`
  - `DEPLOYMENT`
  - `PLATFORM_MANAGED`
- `managedByPlatform` boolean
- `cleanupPolicy`
  - `KEEP`
  - `DELETE_ON_HARD_DELETE`
  - `DELETE_WHEN_UNREFERENCED`

Recommended default rules:

- deployment-owned single-deployment overrides default to `DELETE_ON_HARD_DELETE`
- reusable override secrets default to `KEEP`
- `DELETE_WHEN_UNREFERENCED` is reserved for intentionally shareable secrets with tracked references

### 8.2 Deployment binding model

Do not store raw secret names deep inside provider JSON.

Add an explicit deployment/provider override binding model.

Recommended shape:

- deployment-scoped secret reference records keyed by:
  - `deploymentId`
  - `secretPurpose`
- `bindingMode`
- `secretName` for single-secret purposes
- paired secret-set reference for paired purposes such as `MILVUS_RUNTIME_CREDENTIALS`

Use a dedicated table for deployment override bindings.

Reason:

- binding metadata is not the same thing as secret storage
- it needs auditability, lifecycle, and diagnostics separate from the raw secret row

### 8.3 Why not raw providerConfig fields

Avoid draft JSON like:

- `providerConfig.openaiApiKeySecretName`
- `providerConfig.providerSecretOverrides`

for the persisted source of truth.

A binding table is better because it:

- avoids config sprawl
- keeps secrets governance separate from provider tuning
- supports better audit and cleanup

Draft/UI forms may still present override selectors, but persistence should land in a governed binding model.

## 9) Resolution Contract

Create a dedicated resolver service.

Recommended contract:

- `resolveEffectiveSecret(deploymentId, secretPurpose)`

Recommended output:

- `resolved`
- `secretName`
- `scopeType`
- `ownerType`
- `fallbackUsed`
- `reasonCode`
- `diagnosticMessage`

### 9.1 Reason codes

Persist machine-readable reason codes such as:

- `DEPLOYMENT_OVERRIDE_PRESENT`
- `DEPLOYMENT_OVERRIDE_MISSING`
- `DEPLOYMENT_OVERRIDE_REQUIRED`
- `DEPLOYMENT_OVERRIDE_REQUIRED_MISSING`
- `DEPLOYMENT_MANAGED_PRESENT`
- `GLOBAL_DEFAULT_PRESENT`
- `GLOBAL_DEFAULT_MISSING`
- `NO_EFFECTIVE_SECRET`
- `ENVIRONMENT_FALLBACK_USED`

### 9.2 Required behavior

- resolution must be deterministic
- diagnostics must be able to show the chosen source
- publish/apply verification must be able to fail on missing required secrets
- binding mode must be visible in diagnostics and verification evidence
- secret value must remain hidden from UI and normal audit payloads

## 10) Provider And Runtime Integration

### 10.1 Apply-time behavior

Apply should:

- resolve effective provider secrets for the deployment
- generate `${secret:...}` references against the resolved secret name
- emit verification evidence about the scope used

Apply must not:

- inline raw secret values into deployment artifacts

### 10.2 Runtime env generation

Runtime and connector env generation should continue using secret indirection.

Only the referenced secret name changes.

Example:

- before Track D:
  - runtime env uses `${secret:OPENAI_API_KEY}`
- after Track D for deployment override:
  - runtime env uses `${secret:DEPLOYMENT_OPENAI_API_KEY_DEP_123}` or equivalent internal alias

### 10.3 Managed vector interplay

Managed vector flows keep their existing behavior:

- platform-managed provisioning may still generate deployment-managed runtime secrets

The resolver simply becomes aware of that scope in the precedence chain.

## 11) UX Plan

### 11.1 Secrets workspace

Add explicit override management without exposing raw values after save.

Recommended layout:

- `Global defaults`
- `Deployment overrides`
- `Managed deployment secrets`

For deployment overrides, show:

- purpose
- bound deployment
- effective secret name
- source scope
- present/missing
- last updated
- updated by
- cleanup policy

### 11.2 Providers workspace

Providers should show effective credential source, not secret value.

Examples:

- `OpenAI credential source: deployment override`
- `Pinecone credential source: global platform default`
- `Qdrant runtime key source: deployment-managed`

### 11.3 Diagnostics and source of truth

Add:

- effective secret resolution summary
- fallback chain visibility
- missing override warnings
- publish/apply verification evidence

### 11.4 Validation messaging

If an override binding exists but the secret is missing:

- publish/apply should fail with a precise message
- UI should not silently fall through unless the binding mode is `ALLOW_STANDARD_PRECEDENCE`

## 12) Security And Governance

### 12.1 Hard rules

- no raw values in drafts
- no raw values in source-of-truth payloads
- no raw values in diagnostics responses
- all writes audited
- all binding changes audited
- all cleanup actions audited

### 12.2 Access control

Recommended:

- platform admin
  - can create, rotate, bind, unbind, and delete any override
- deployment admin
  - can bind and unbind allowed overrides only for assigned deployments
  - cannot create or rotate raw override values in phase 1
- deployment operator
  - can see effective source and presence, not mutate override values
- deployment viewer
  - can see high-level source state only if workspace rules already allow provider visibility

### 12.3 Approval posture

Do not require approval for simple bind or unbind in phase 1.

Raw secret value creation or rotation remains a platform-admin action in phase 1.

Do require normal approval rules if an override change is part of a governed apply/delete path already protected by approvals.

---

## 13) Lifecycle And Cleanup

### 13.1 Unbind behavior

If an override binding is removed:

- effective resolution falls back to deployment-managed secret if present
- otherwise global default
- otherwise validation fails where the secret is required

### 13.2 Hard delete behavior

On hard delete:

- remove deployment override bindings
- delete deployment-owned override secrets with cleanup policy `DELETE_ON_HARD_DELETE`
- delete `DELETE_WHEN_UNREFERENCED` secrets only after reference count reaches zero
- keep global secrets
- keep unrelated deployment overrides
- keep reusable bound secrets whose lifecycle is not owned by the deleted deployment
- keep deployment-managed secrets only according to their existing cleanup rules

The platform must distinguish clearly between:

- a secret row owned by the deleted deployment
- a reusable secret row that was merely bound to the deleted deployment

### 13.3 Archive behavior

Archive should not automatically delete deployment overrides.

Archived deployments may still be restored or inspected.

Cleanup belongs to:

- explicit override deletion
- hard delete

---

## 14) Migration Strategy

This feature must be additive.

Initial rollout behavior:

- no existing deployment changes behavior automatically
- all existing deployments continue using global defaults or current deployment-managed secrets
- overrides activate only when an operator explicitly binds one

### 14.1 Backfill

Backfill only metadata needed for current secrets:

- global platform secrets become `GLOBAL_PLATFORM`
- current platform-generated deployment secrets become `DEPLOYMENT_MANAGED`

No deployment override bindings should be auto-created.

## 15) Verification And Regression Requirements

Track D is not complete without real regression coverage.

### 15.1 Local/backend coverage

Required tests:

- secret scope resolution precedence
- binding mode behavior for `REQUIRE_OVERRIDE` versus `ALLOW_STANDARD_PRECEDENCE`
- missing override with valid global fallback
- missing override with no fallback
- deployment-managed secret precedence over global
- paired-credential override resolution for Milvus runtime credentials
- deployment hard delete cleanup for deployment overrides
- reusable override secret survives deployment hard delete after binding removal
- audit records for bind/unbind/update/delete
- provider diagnostics showing effective source

### 15.2 Live/admin verification

Required live checks:

- platform admin creates a deployment override
- deployment admin binds and unbinds an existing allowed override for an assigned deployment
- provider diagnostics show `DEPLOYMENT_OVERRIDE`
- apply uses override successfully
- removing the binding falls back to global
- hard delete removes deployment-owned override artifacts

### 15.3 Negative verification

Required negative cases:

- override binding points to missing secret
- unsupported secret purpose attempted as override
- deployment admin tries to manage another deployment’s override
- deployment admin tries to create or rotate a raw override value
- paired Milvus credential override missing one half of the credential set

## 16) Detailed Implementation Items

These are the implementation items to review and then execute in order.

### Foundation

1. extend the platform secret model with explicit scope, owner, purpose, and cleanup metadata
2. introduce a deployment override binding model keyed by deployment, secret purpose, and binding mode
3. backfill current global and deployment-managed secrets into the new metadata model

### Resolver and contracts

4. implement an effective secret resolution service with explicit precedence and reason codes
5. expose effective secret resolution summaries to diagnostics, provider connectivity, readiness, and source of truth
6. update env-generation and apply-time secret reference compilation to use resolved secret names

### Validation and governance

7. add publish/apply validation for missing required override bindings, missing referenced secrets, and incomplete paired credentials
8. add permission checks that keep raw secret value mutation platform-admin only while allowing deployment-admin bind or unbind on assigned deployments
9. add audit events for override create, update, bind, unbind, delete, and cleanup

### UI and APIs

10. add deployment override management APIs in the platform backend
11. add `Secrets` workspace support for deployment overrides and effective source visibility
12. add `Providers` workspace effective credential source summaries and fallback warnings

### Cleanup and lifecycle

13. add hard-delete cleanup for deployment override bindings and deployment-owned override secrets, while preserving reusable bound secrets
14. add archive-safe behavior and explicit override deletion flows

### Verification and release

15. add backend regression coverage for precedence, governance, diagnostics, and cleanup
16. add hosted/admin verification flows for real override resolution and cleanup proof
17. update GitHub live regression so deployment override behavior can be exercised intentionally

## 17) Locked Review Decisions

The following review decisions are now closed for Track D phase 1:

1. Supported override-purpose list:
   - keep the provider and data-plane list
   - treat Milvus runtime credentials as one paired purpose: `MILVUS_RUNTIME_CREDENTIALS`
2. Binding model:
   - use a dedicated binding table
   - do not persist override refs in `providerConfigJson` or versioned config metadata
3. Deployment-admin permission boundary:
   - deployment admins may bind or unbind allowed overrides for assigned deployments
   - raw override value creation and rotation remain platform-admin only in phase 1
4. Cleanup defaults:
   - deployment-owned single-deployment secrets default to `DELETE_ON_HARD_DELETE`
   - reusable secrets default to `KEEP`
   - `DELETE_WHEN_UNREFERENCED` applies only when the platform can prove no bindings remain
5. Management-plane secrets:
   - remain global in phase 1
   - no exception is currently approved for `QDRANT_CLOUD_MANAGEMENT_API_KEY`, `ZILLIZ_CLOUD_API_KEY`, `PLATFORM_ARTIFACT_SIGNING_KEY`, or ingress/admin auth keys

## 18) Completion Criteria

Track D is complete when:

- deployments can bind supported provider purposes to deployment-owned override secrets
- fallback behavior is explicit through binding mode and never silently ambiguous
- effective resolution precedence is deterministic and visible
- raw secret values never appear in draft/config/source-of-truth payloads
- apply/runtime generation uses resolved secret references correctly
- validation blocks broken override bindings
- paired credentials such as Milvus runtime auth resolve atomically
- hard delete cleans deployment-owned override artifacts safely
- reusable secrets are preserved when only the binding should be removed
- local regression and live admin verification both prove the feature

## 19) Recommendation

This track should proceed only after Track B verification closure is stable.

But once Track B closes, Track D is a valid next execution target even if Track C remains deferred.

That sequencing is justified because:

- Track D strengthens enterprise isolation and customer-owned credential boundaries
- Track D builds on the now-real tenant, vectorization, and verification foundations
- Track C is valuable, but not required to unblock enterprise credential isolation
