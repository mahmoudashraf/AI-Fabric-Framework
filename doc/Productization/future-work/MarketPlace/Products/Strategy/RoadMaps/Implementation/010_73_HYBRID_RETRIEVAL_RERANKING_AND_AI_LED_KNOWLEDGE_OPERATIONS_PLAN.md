## 1. Outcome And Decisions For Review

Give customers one coherent way to make their knowledge searchable, improve the
information supplied to AI, and inspect whether the changes actually helped.
Support both approved document chunks and indexed business entities, such as
products, vehicles, services and support records. Do not build a document-only
optimization path and leave entity search behind.

Recommended delivery order:

1. Establish reviewed evaluation sets and a reproducible dense-search baseline.
2. Implement genuine lexical plus vector retrieval with reciprocal rank fusion
   (RRF), initially for the managed Milvus path and both data types.
3. Expose customer search settings, shared evaluation comparisons and AI-assisted
   optimization through the existing Brain workspace.
4. Complete bulk discovery-to-indexing for existing S3 files and Console uploads;
   let the existing assistant coordinate the bounded, customer-approved journey.
5. Add optional learned reranking behind a provider-neutral interface. Qualify
   one hosted adapter first; do not add GPU infrastructure by default.
6. Publish compatible releases, deploy through the normal lifecycle, and qualify
   the complete customer journeys on staging and production.

Review choices proposed here:

- Managed-provider-first hybrid implementation; no mandatory replacement of all
  customer vector services and no new search-server requirement.
- Equal-weight RRF initially. Tune weights only against reviewed evidence.
- Ragas is the selected evaluation engine behind LoomAI's existing workflow,
  for documents and entities. Customers do not choose or operate an evaluation
  framework. This decision replaces an open-ended evaluator-tool comparison;
  the adapter and rollout remain implementation work, not a live capability.
- One optional hosted reranker adapter, recommended Cohere Rerank, subject to
  approved credentials, provider data processing and spending limits.
- Existing configurations remain unchanged. Hybrid and reranking become explicit
  choices; qualification, not a feature flag, determines later template defaults.
- One confirmation authorizes an exact operational indexing plan, not an entire
  bucket, future files, broader access or automatic production publication.

## 3. Scope And Non Goals

Documents use approved extracted text, chunk/page attribution, source versions,
visibility and processing profiles. Entities use their existing approved field
projection, entity type, identity, version and source authorization. Both enter
the same retrieval/ranking/evaluation architecture, but do not share every
preparation control: OCR settings do not belong on a product record.

Mixed searches may include both when the Brain's authorized source catalogue and
configured retrieval scope allow it. Supporting both does not mean searching
every namespace by default or granting a new cross-source fan-out permission.

Non goals:

- No new plugin categories, arbitrary connector protocols, customer account types
  or replacement Console shell. Keep the accepted Brain workspace and UI journeys.
- No autonomous business writes, source-object deletion or database migration by
  the assistant. Indexing is a separate, explicitly authorized operational task.
- No public web search, general code-execution agent or unbounded folder watcher.
- No automatic new servers, GPU service, paid capacity, provider subscription,
  storage expansion or changes to the two-environment allowance.
- No claim that reranking fixes missing source data, poor extraction, wrong tool
  selection, contradictory policies or every specialist reasoning failure.
- No automatic public approval, production apply or Engage activation.

## 4. Customer Stories

### Existing S3 Documents

Customer: "Make the documents in my support folder searchable."

The assistant resolves the selected Brain, target, applied release and owned
connection. It asks for a folder only if no sufficiently specific folder is
selected. It discovers a bounded inventory, shows eligible/changed/unchanged and
unsupported files, inspects authorized samples and prepares a reviewable plan.

The plan names the exact files, destination, audience, processing settings,
sampling coverage and finite AI/indexing/evaluation allowances. A single customer
confirmation starts the approved work in bounded batches. The assistant follows
actual receipts and reports searchable files, pending work and individual errors.
It evaluates saved questions and offers changes justified by the actual results.

"18 searchable, 2 need attention" is illustrative copy, not a hardcoded result.
Only observed counts may be shown. New files arriving after review are not added
silently, and successful upload/queue acceptance is never called searchable.

### Entity Knowledge

Customer: "Improve how customers find the right products and compare options."

The assistant uses the selected live-data source and declared entity mapping. It
reviews approved searchable fields and an authorized sample, proposes a search
profile, and prepares test questions covering identifiers, paraphrases, filters,
similar products and missing information. It compares dense and hybrid retrieval
against the same entity snapshot, then optionally evaluates a learned reranker.

If a connector supports authorized seed/read synchronization, the existing sync
workflow can populate its index after review. If it is push-only, the UI states
that the customer's backend must send the existing Data Sync events. The assistant
must not invent a "list all records" endpoint, database access or new plugin type.

JSON documents remain documents. JSON becomes entity ingestion only through an
explicit supported entity mapping, not because of its file extension.

## 5. One Shared Retrieval Architecture

```text
Question + selected profile + trusted authorization/source scope
                             |
                 Resolve eligible source catalogue
                             |
              +--------------+---------------+
              |                              |
       Dense vector candidates        Lexical BM25 candidates
              |                              |
              +--------- same owner, audience, version filters
                             |
              Canonical candidate identity / deduplication
                             |
                     RRF fusion, once
                             |
               Optional learned reranker, bounded
                             |
                 Final context/evidence selection
                             |
                 Answer generation and evaluation
```

### Implementation Ownership

- Core owns typed requests, identity, source contracts, capabilities and budgets.
  Do not introduce a core-to-RAG implementation dependency.
- Vector/source adapters own dense/lexical primitives and provider-specific
  indexes. They must apply the same server-owned authorization filters.
- `ai-fabric-rag` owns fusion, optional reranking and context selection. Reuse
  `RAGProvider.performRag` as the retrieval-only entry for evaluations and proofs;
  extend its typed options rather than adding another public search engine.
- Refactor `RAGSearchExecutor`, `RAGService` and Advanced RAG to share that
  implementation. Do not run fusion or reranking twice when Advanced RAG is used.
- Runtime adapters preserve document active manifests, approved entity projections
  and current access checks before evidence is exposed to models or callers.
- Platform compiles owned draft settings, checks capabilities, proxies customer
  operations, and owns customer-facing operational coordination.

Keep existing chat/query endpoints. New settings are deployment configuration,
not permission for a widget request to choose credentials, tenants or arbitrary
retrieval resources. Keep LLM-driven source/tool decisions within the configured
catalogue; do not route queries by regex, identifier patterns or keyword lists.
BM25 is an explicit retrieval algorithm, not a replacement for LLM intent planning.

### Candidate Identity And Scores

Document identity includes source, active version and chunk identity. Do not
collapse all chunks of a document into one result. Entity identity includes
source, entity type, entity ID and version; identical IDs in different sources
must not collide. Preserve original records and attribution while merging ranks.

Keep vector similarity, lexical score, fusion rank/score and reranker relevance
separate. A dense threshold must not filter BM25 or RRF scores. Neither a score
nor a percentage is an answer-correctness probability. Preserve legacy response
contracts where needed, but display truthful score types and effective search
mode; do not label an RRF value as a percentage confidence.

## 6. Hybrid Retrieval First

### Provider Contract And Milvus Qualification

Implement keyword retrieval and genuine hybrid capability in the managed Milvus
adapter, with a version-matched SDK upgrade if needed. Qualify current server,
SDK, authentication, full-text functions, analyzer behavior, filtering and index
schema before choosing the exact library/server versions.

Start with two scoped retrieval legs and framework-owned RRF. A native hybrid
optimization is acceptable only with a declared fusion owner and equivalent
security/trace semantics. Never apply native fusion and framework fusion twice.
No automatic additional Lucene sidecar or external search service for BYO stores.

Capability must be reported per resolved corpus/index generation as well as
provider implementation. A provider supporting hybrid in principle is not proof
that an older customer collection has a ready lexical index. Unsupported BYO
providers keep their existing dense path and show the limitation explicitly.

BM25 indexes the same approved document text/entity projection as dense indexing.
Test analyzers with supported languages, punctuation, error codes and declared
identifier fields. Field selection comes from the existing entity/source schema;
no business-specific list of special words is added to framework code.

### Index Lifecycle

1. Define an additive index generation containing lexical text/index state and
   existing dense fields, ownership metadata and source/record versions.
2. Backfill from canonical approved originals/projections through existing
   document/entity indexing queues; reuse valid embedding caches when applicable.
3. Keep the serving generation available. Catch up changes through the existing
   durable ingestion sequence/work receipts before a generation switch.
4. Activate only when both retrieval legs are ready for the required data, with
   an atomic generation/version check. An accepted backfill is not readiness.
5. Upserts, document replacement and deletes must update or retire both legs.
   Stale lexical hits must never resurrect removed or unauthorized evidence.
6. Keep a bounded rollback option only while its data remains current. Either
   maintain/catch up the previous generation or state that rollback requires
   rebuilding; never silently switch back to stale records.

Collection/schema work must preserve quotas and existing resource identity.
Measure disk/memory headroom before backfill. If a server/service upgrade,
replacement or additional paid capacity is required, stop for explicit owner
approval with cost, availability and rollback implications. A software-release
request does not approve those infrastructure changes.

Do not use vectors copied from staging for production promotion. Production
indexes its selected approved originals/projections in its own authorized scope.

### Fusion And Failure Behavior

Use RRF over ranked candidate lists, with deterministic tie-breaking and explicit
deduplication. Initially use equal weights and a documented rank constant. Query
expansion adds tagged candidate lists within the same request-wide budgets; do
not allow expanded queries to create uncontrolled calls or duplicate fusion.
Disable expansion consistently in the first A/B comparison to isolate hybrid's
effect; qualify expansion interaction separately.

Configuration cannot report HYBRID when the actual adapter used dense fallback.
For transient lexical failure, a published explicit degradation policy may keep
authorized dense evidence and report the effective mode/failure. A strict
customer retrieval requirement may instead stop the operation. No degradation
relaxes authorization, funding or source restrictions, widens search, or
substitutes a canned answer.

## 7. Optional Learned Reranking

Add a small provider-neutral `RerankingProvider` SPI in core, with an optional
provider adapter module, used by the common RAG implementation. It accepts the
resolved question, bounded authorized candidate texts/IDs and finite execution
options; it returns candidate references, relevance scores and usage/diagnostics.

Qualify one hosted adapter first, proposed Cohere Rerank. Model/provider selection
is explicit; no "latest" model alias is silently substituted during evaluation.
Self-hosted cross-encoders remain a later adapter behind the same contract, not
a compulsory Python service or a new GPU deployment in this implementation.

Required behavior:

- Only authorized candidate content reaches the external service. Preserve exact
  source IDs, versions, ownership and approved entity projections afterward.
- Validate result identity/index bounds, duplicate references and finite scores
  as an execution contract. A provider cannot inject new documents or fields.
- Bound candidates, text/tokens per candidate, deadline, concurrency and calls.
  Record truncation, provider/model and actual billed units where available.
- Keep accounting integrated with the existing funded/direct-provider modes.
  Funded denial never falls back to unbudgeted credentials. Unknown cost is not 0.
- Store credentials through Keys & secrets and existing delegation, never in
  assistant context. Provider enablement must disclose that selected text is
  processed by that recipient; no silent third-party document sharing.
- Optional failure may retain the authorized pre-rerank order only under the
  configured visible failure policy. Do not replay writes, retry indefinitely,
  fabricate relevance or call reranking successful when it was skipped.
- Preserve existing embedding-rescore strategies as accurately named legacy
  behavior until explicitly changed. Do not market score blending as learned
  reranking or as genuine hybrid retrieval.

Default learned reranking is OFF until a reviewed comparison supports enabling
it for that profile/template. A reranker cannot recover an absent candidate.

## 9. Comparable Evaluation For Documents And Entities

### Selected Engine: Ragas Behind LoomAI

Use the Ragas library as the managed evaluation implementation behind
`RagEvaluationProvider`. Keep Evaluate, Compare results and Improve with AI in
the existing Console and shared assistant. Do not add a Ragas/DeepEval/custom
judge selector, separate customer login, dashboard or required hosted Ragas
account. Provider extensibility is an internal framework boundary, not another
customer configuration task. DeepEval is not an additional implementation in
this plan; the existing Spring AI adapter remains a library extension point.

Ragas is selected for its explicit metric procedures and retrieval coverage,
not because it has guaranteed access to truth or is proven more accurate here.
Its model-based metrics still use a configured LLM; some use embeddings or a
specialized consistency model, while reference-ID ranking metrics use direct
calculations. A library name is not an accuracy guarantee. Initially use the
Brain's supported model/embedding bindings through controlled adapters, not a
new mandatory provider or a model chosen silently by the Python SDK.

Required measurement coverage:

- Faithfulness against the actually supplied excerpts, using Ragas' supported
  claim-checking procedure instead of relabelling our current direct score.
- Answer relevance using the selected version's supported Ragas metric and its
  declared model/embedding requirements.
- Context precision/recall where the required references or labels exist.
  Model-judged context recall and exact-ID Recall@k are different measurements;
  store their method and inputs rather than presenting them interchangeably.
- Reviewed-reference correctness/agreement when an expected answer exists,
  with the chosen Ragas metric identified explicitly. Missing prerequisites
  produce NOT_SCORED. Synthetic references remain clearly unreviewed.
- Recall@k, MRR and nDCG@k calculated from reviewed identities/graded relevance
  labels, without an unnecessary LLM call for the arithmetic.

Faithfulness means consistency with retrieved text, not real-world correctness.
A wrong or obsolete source can support a faithful but wrong answer. Likewise,
the judge may miss a contradiction or be influenced by a wrong reference.
Calibrate on a reviewed held-out set containing supported answers, invented

Account for every answer, metric sub-call, embedding request and allowed retry
