# Install And Operate A Support Experience

This guide describes the native Desk ticket provider and the reusable
`support@1.0.0` experience. A page, website widget and standalone app can share
one support deployment. They are delivery options, not separate AI products.

## Owner Setup

Your workspace needs an available published support template/profile. A team
publishing a new catalogue offer must select the current qualified runtime
artifact explicitly; older immutable offers remain historical bootstrap
snapshots. Do not reuse LoomAI's private support profile, documents, credentials
or canary funding as public defaults.

1. In Console, select the AI Support Experience kit and its support template.
   Choose the app address and website/standalone delivery options.
2. Connect your approved document storage and model/provider settings. Source
   files stay in your storage. Supply a scoped reader; do not make the bucket
   public or paste credentials into the chat. Index approved documents and
   verify retrieval against the selected deployment target.
3. Enable ticketing against the configured native Desk provider. Ticketing does
   not require human handover. If human assistance is wanted, enable the channel
   and assign registered agents to that deployment target with SUPPORT access.
4. Configure the support name, theme, topics, welcome text and optional tools.
   The preview is illustrative; it neither provisions a provider nor proves
   that agents are online.
5. Publish/apply the deployment through its existing version/release flow.
   Connect the Engage installation to the verified assignment, configure its
   support space, pass readiness and activate explicitly.
6. Open the app or copy its installation script. Test a real signed-in requester,
   a saved request, canonical answer restoration and any enabled human handover.

Templates supply initial settings. Later changes use the normal draft,
publish, apply and verification lifecycle. Resetting template settings changes
the draft only; it does not replace credentials or delete indexed documents.

## Website Installation

Use the actual installation ID generated by Console. Never put a runtime key,
provider secret, private assertion or requester access token in HTML.

Contained support page:

```html
<div id="support-root" style="height: calc(100dvh - 96px); min-height: 480px"></div>
<script async
  src="https://api.loomai.pro/api/public/ai-workspace/install.js"
  data-installation-id="YOUR_PUBLIC_INSTALLATION_ID"
  data-presentation="page"
  data-container="#support-root"></script>
```

Floating support widget:

```html
<script async
  src="https://api.loomai.pro/api/public/ai-workspace/install.js"
  data-installation-id="YOUR_PUBLIC_INSTALLATION_ID"
  data-presentation="widget"></script>
```

Register the exact HTTPS website origin. The standalone app uses its activated
app address. In a SPA, install once in the persistent layout; do not remount on
each route. The contained target needs a bounded height. Layout/minimization
preserves the conversation; explicitly choosing another ticket/episode changes
the conversation scope.

## Identity And Private Applications

The qualified direct mode uses configured Supabase sign-in. An original
Supabase requester token authorizes Desk; a separate, scoped runtime credential
authorizes AI conversation access. They are not interchangeable. The installer
obtains these through the registered authentication contract, not from model
parameters or an email supplied in a form.

Standalone Engage provides its sign-in screen. An embedded authenticated
installation uses the website's existing sign-in through trusted host callbacks
set **before** loading the installer. The script alone does not invent a website
login or recover a token from an unrelated application. For example, using the
website's already initialized Supabase client and current verified session:

```ts
window.LoomAIWorkspaceHost = {
  version: '1.0.0',
  identity: session
    ? { status: 'authenticated', subjectKey: session.user.id }
    : { status: 'anonymous' },
  getIdentityAccessToken: async () =>
    (await supabase.auth.getSession()).data.session?.access_token ?? null,
  requestSignIn: () => openWebsiteSignIn(),
  signOut: () => signOutOfWebsite(),
}
```

After a real sign-in/sign-out/account switch, reload the host document to mount
the new identity; do not substitute another person's token into a running
conversation. Ordinary same-user token refresh uses the callback without a
reload. Public AI can be configured independently, but protected ticket access
still requires a configured identity path. No customer backend is needed for
this direct Supabase browser integration.

LoomAI Console uses the same pack with a thin private-host adapter for its
existing private runtime and diagnostic consent. That adapter is not a universal
backend for external customers. See [the host adapter contract](CONSOLE_HOST_ADAPTER.md)
for a reviewed private application integration. Arbitrary identity providers
and external helpdesk vendors require an explicit adapter and qualification.

Sign-out/account changes clear the prior requester scope. Same-user token
refresh preserves the mounted conversation. My Requests lists only the
authenticated requester's own tickets; a ticket reference grants no access.

## Requests, AI And Human Assistance

- Request help saves the request first, returns a provider reference, and then
  delivers its opening message to the canonical AI conversation. Save and AI
  delivery have separate outcomes.
- A user can start with chat and explicitly link that existing owned
  conversation to a request. Linking does not resend the conversation or intake.
- An installed AI ticket action proposes its details and requires its declared
  confirmation. The request exists only after a successful provider receipt.
- My Requests supports the provider's actual list/detail, updates and explicit
  resolve, cancel and reopen capabilities. Unsupported commands are not faked.
- Request status is separate from AI/human conversation control. Resolving a
  request is not returning to AI. Reopening does not replay intake or restore
  diagnostic consent.
- Previous episodes remain readable. Continuing after a closed conversation
  creates a new empty episode, not a copied transcript or repeated AI request.
- When enabled, Talk to a person uses the existing handover channel. A named
  assigned agent is not a claim of current availability or response time.

## Agent Workflow

An agent first registers/signs in to LoomAI Desk. A customer owner assigns that
agent to the deployment target using its registered agent reference and SUPPORT
role. An agent may have multiple separately authorized assignments.

In Desk, select the assigned deployment, inspect its requests/conversations,
claim a pending handover and reply. Replies reach the requester through the
existing conversation channel without requiring another AI query. Returning to
AI and closing a conversation are explicit authorized operations. REVIEWER
access to action reviews remains a separate permission.

## Storage And Retention

- Native Desk owns ticket text, status, versions, operation receipts, requester
  scope and episode links in its shared multi-customer database. There is no
  additional per-deployment ticket database.
- The runtime owns canonical AI/human conversation state in its configured AI
  state store. Desk links to it rather than duplicating transcripts as tickets.
- Original knowledge files remain in the customer's S3-compatible storage;
  derived indexed evidence remains in the selected vector service.
- Console retains only its resource/consent context and authorized integration
  receipts. Its former separate ticket store is retired.

Configure the provider's retention policy deliberately. Erasure, ticket closure
and conversation closure are different operations. Native purge uses an
authorized, idempotent receipt; do not delete source documents or unrelated
customer state as a side effect of closing a support request. External ticket
providers, when implemented, own their own retention rather than replicating
their complete ticket store into Desk.

## Failures And Release Checks

If ticket save or an action outcome is uncertain, keep its operation key and
inspect the actual receipt. Do not create a replacement request, change
providers, repeat confirmation or replay intake automatically. A saved ticket
with failed AI delivery stays saved and displays the separate delivery state.
Provider errors remain visible; no private Console fallback is used.

In-app updates are the qualified notification channel. Email delivery requires
an implemented and separately configured delivery integration; it is not
enabled or claimed by this release.

Before opening a new installation, verify: exact assignment and active source
evidence; real sign-in/sign-out; own/foreign ticket isolation; request receipt
and answer restoration; lifecycle/version conflicts; enabled/disabled human
behavior; agent reply and return to AI; both chosen delivery layouts. Evaluate
AI answer quality separately from HTTP/health results. Known wrong-subject
follow-ups are not successful answers just because the request returned 200.

Specific external helpdesk adapters, omnichannel inboxes, SLAs, organization-wide
requester access and autonomous remediation remain outside this first release.
